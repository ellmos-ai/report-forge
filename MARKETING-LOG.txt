## 1. Executive Summary & Positionierung

`report-forge` ist die domänen-neutrale Kern-Engine für schema-gebundene, datenschutzkonforme Berichts- und Gutachten-Pipelines:
1. **Drei-Phasen-Architektur**: Strikte Trennung von Extraktion (`prepare`), Inferenz (entkoppeltes LLM) und Validierung/Rendering (`finish`).
2. **Datenschutz durch Design (DSGVO Art. 4(5))**: Umschaltbar zwischen Fail-Closed Anonymisierung (`mode="anonymized"`, Integriert mit `anonymizer` >=0.2.5) und unverschlüsseltem Modus (`mode="plain"`).
3. **Deterministische Word-Vorlagenengine**: Präzises Auffüllen von `.docx`-Dateien (`{{PLATZHALTER}}`, dynamische Tabellenzeilen, Checkboxen) basierend auf JSON-Schema (Draft 2020-12 / Draft 7).
4. **Automatisierte Batch-Verarbeitung**: Idempotenter `process-inbox`-Runner mit atomarer Veröffentlichung (`output_dir`) und Zeitstempel-Kollisionsschutz.

## 2. Ziel-Personas (Target Audience)

### Persona 1: Enterprise Data Protection Officers (DPO / CISO)
- **Problem**: Unternehmen und Behörden wollen LLMs zur Berichterstellung nutzen, dürfen aber keine personenbezogenen Daten (PII) wie Klientennamen, Geburtsdaten oder Adressen an externe LLM-APIs leiten.
- **Lösung mit report-forge**: `mode="anonymized"` sorgt dafür, dass vor dem Prompt-Bau alle PII deterministisch pseudonymisiert und verschlüsselt werden. Das externe LLM sieht nur neutrale Tokens. Erst bei der lokalen Finalisierung (`finish`) werden die Daten auf vertrauenswürdigen Systemen wiederhergestellt.

### Persona 2: Clinical, Diagnostic & Educational Reporting Engineers
- **Problem**: Fachkräfte (z. B. Psychologen, Sonderpädagogen, Gutachter) verbringen Stunden mit dem manuellen Verfassen repetitiver Entwicklungs- und Förderberichte.
- **Lösung mit report-forge**: Domänenspezifische Overlays (wie `foerderplaner`) nutzen `report-forge` als stabilen Unterbau. Quelldokumente (PDF, DOCX, XLSX) werden aggregiert, strukturierte Berichte per Schema validiert und druckfertige Vorlagen im CI-Design der Organisation befüllt.

### Persona 3: Legal & Regulatory Audit Tech Developers
- **Problem**: Automatisch generierte juristische oder Compliance-Berichte leiden häufig unter LLM-Halluzinationen oder unvollständigen Abschnitten.
- **Lösung mit report-forge**: Strenge JSON-Schema-Validierung als hartes Gate vor der Vorlagenbefüllung. Bei Schema-Verletzungen bricht der Prozess ab (Fail-Closed), anstatt fehlerhafte Dokumente zu erzeugen.

### Persona 4: Autonomous AI Agent Architects & Local-First Developers
- **Problem**: Autonome Agentenframeworks (wie `coma` oder `rinnsal`) benötigen modulare, prozessfreie CLI-Werkzeuge zur Erstellung finaler Artefakte ohne Netzwerk-Egress.
- **Lösung mit report-forge**: Vollständig zustandslos oder sitzungsbasiert steuerbar, 100% offline-fähig, keine versteckten Telemetrie- oder API-Aufrufe.

## 5. Integrations-Blueprints

### Blueprint A: Automatisierter Batch Inbox Runner (Cron / Headless Service)
```bash
# Periodische Ausführung (z. B. via systemd timer oder Windows Task Scheduler)
python -m report_forge process-inbox \
  --work /var/lib/report_forge/sessions \
  --mode plain \
  --config /etc/report_forge/config.json
```

### Blueprint B: Python Pipeline Einbindung
```python
from pathlib import Path
from report_forge.workflow import ReportWorkflow

workflow = ReportWorkflow()

# Phase 1: Intake & Prompt Generation
prepared = workflow.prepare(
    source_folder=Path("inputs/case_042"),
    work_root=Path("sessions/"),
    mode="plain",
)

# Phase 2: Inferenz über externes LLM (z. B. Ollama / Gemini / Claude)
# [llm_generate(prompt=prepared.prompt_path.read_text()) -> "sessions/.../report.json"]

# Phase 3: Validierung & Rendering
result = workflow.finish(
    session_dir=prepared.session_dir,
    llm_json_path=prepared.session_dir / "data_bundled" / "report.json",
    output_folder=Path("dist/reports/"),
)
print(f"Report successfully rendered to: {result.output_path}")
```
